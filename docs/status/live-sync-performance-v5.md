# 实时同步 V5 性能复用状态

**日期：** 2026-09-02

**分支：** `develop`

**状态：** 一条开发态真实两步事件已在 500 ms 内正确接受；Stage C 正式冻结门仍未通过

## 本轮目标

V5 已能安全处理天天象棋最后一步光圈，但此前两条真实开发事件的决策延迟分别约为
569 ms 和 551 ms，高于 Stage C 的 P95 500 ms 硬门。本轮不修改任何识别阈值，而是删除
重复计算：

- 已确认局面的 90 点占位结果在 tracker 内缓存；接受事件后只重新计算已经规则层与视觉层
  共同确认的走法变化点。单步使用起终点，连续应手使用最终候选的 1 至 4 个语义变化点。
- 同一终局小裁片的颜色特征与全部模板距离只计算一次，再供不同候选和语义分组复用。
- 单步观察器与双步观察器共享同一已确认帧的模板库；确认帧、局面、几何或裁片尺寸变化时
  自动失效并重建。
- 棋子转移对齐范围固定为真实样本已验证的 ±1 像素；最低语义置信度仍为 0.8，候选分数、
  候选间距、链外变化、棋规和占位硬门均未降低。

## 测试先行证据

新增测试先在旧实现上失败，分别证明旧实现：

1. 没有可复用的裁片分类结果；
2. 同一终局交点会因不同候选被重复提取特征；
3. 单步与双步观察器会从同一确认帧重复建立模板库；
4. 已接受事件仍会重新扫描全部 90 个占位点。

实现后，同一小裁片最多分类一次，同一确认帧只建立一次模板库，增量占位结果保持完整
90 点证据结构，拒绝和异常路径仍使用完整扫描。

独立代码评审随后发现：若直接用原始画面差最大的四点做增量更新，落子光圈、阴影或提示
标记可能挤掉真实端点，并污染下一回合的确认基线。新增回归先复现该问题，再改为：

- 已接受单步只采用已验证走法的起点与终点；
- 已接受连续应手只采用排名第一且已核对 `moves` 与 `position_id` 的候选变化点；
- 只有拒绝事件的诊断小裁片继续按原始画面差取前四点；
- 模板缓存改为一次替换的不可变条目，并完整覆盖局面、几何、确认帧身份和裁片尺寸失效键。

- 当前固定主题、红方在下、可见无遮挡窗口的单次真实结果已低于 500 ms，且没有通过降低
