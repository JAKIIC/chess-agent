# Accelerated Batch 1.2：变化触发的突发采样

**日期：** 2026-08-30

**分支：** `develop`

**起始检查点：** `700d245a8b64fb1b5f3ea9db2e19911356f1e20e`
**结论：** 已实现“高频变化回调 + 2 FPS 稳态逻辑 + 静默端点保留”的最小采样闭环。离线测试证明：即使下一次变化已经到达，也会先把此前保持稳定的上一帧交给严格走法观察器。真实棋盘成功建立两步后局面的基线，但 90 秒监听期间没有发生落子，因此本批没有取得新的真实单步证据。

## 1. 范围和安全边界

本批只修改真实观察探针的采样节奏：

```text
WGC 以最高 20 FPS 接收变化回调
  → 稳态回调只缓存，逻辑时钟保持 2 FPS
  → 连续 100ms 无新回调时提升最后一帧为稳定端点
  → 连续变化在 2 FPS 采样发现棋盘运动后进入突发状态
  → 用两个稳定时钟样本提交给 StableMoveTracker
  → 唯一高置信合法着才更新，否则暂停
```

没有实现 UI、自动定位、ONNX、Pikafish、DeepSeek、SQLite 或打包。程序仍不点击、不自动走棋、不注入、不读取微信进程内存，只处理可见且无遮挡的目标窗口。

## 2. 实现

### `AdaptiveBurstSampler`

新增可独立测试的采样策略，输入仍是现有 `CaptureFrame`，不依赖 WGC 具体实现：

- 稳态时钟默认 2 FPS。
- 突发静默窗默认 100ms，稳定重复数默认 2。
- 捕获回调时间戳必须严格递增；乱序帧立即拒绝。
- 稳态期间只缓存高频回调，不让回调推迟或绕过 2 FPS 时钟。
- 缓存帧若保持 100ms 安静，会以“一个变化样本 + 两个稳定样本”提升为候选端点。
- 突发期间若相邻回调间隔达到静默窗，先输出已处理上一帧的两个稳定重复，再输出新变化帧。
- 如果没有下一次回调，时钟到达静默窗后结算最后一帧。
- 同一个最后帧只结算一次，避免安静窗口反复触发观察。
- 离开突发状态后恢复低频稳态时钟。

这个设计解决了 Batch 1.1 的关键丢帧点：旧探针每 0.5 秒只取队列中的最新帧，可能直接把“用户一步 + 人机一步”合并；新探针按回调顺序处理，并利用捕获时间戳恢复两次变化之间真实存在的安静端点。

### 探针接线

`probe_move_observer.py` 新增：

- `--capture-fps`，默认 20，只控制 WGC 最小更新间隔。
- `--fps` 继续表示稳态逻辑频率，默认 2。
- `--settle-ms`，默认 100。
- 基线输出采样参数，便于复现实验。
- 每批已到达事件先检查关闭信号，再验证全部帧尺寸，之后才能返回旧端点；总超时和观察器异常继续沿用既有安全路径。

采样器不改变 `FrameSource`、`BoardGeometry`、`MoveObserver` 或 `StableMoveTracker` 的契约，未来可以替换捕获后端或观察算法。

## 3. 测试先行证据

第一轮新增测试因 `xiangqi_agent.capture.adaptive_sampling` 不存在而收集失败；最小实现后 8 项采样策略测试通过。第二轮探针接线测试首次因 `_next_adaptive_samples`、`capture_fps` 和 `settle_ms` 不存在而出现 3 个预期失败；接线后通过。

独立评审随后发现两个回归：稳态回调实际绕过 2 FPS，以及已入队关闭/尺寸变化可能被旧端点抢先结算。修复前新增测试出现 7 个预期失败；改为稳态缓存、静默提升和事件批预检后通过。

复审进一步发现静默时钟恰好到期时仍可能跳过已入队事件。新增“到期时关闭”和“到期时尺寸变化”测试均先失败；事件轮询调整为始终先于时钟结算后通过。

覆盖行为包括：

- 新变化到达前的安静端点不会被覆盖。
- 无新回调时由静默时钟结算端点。
- 连续 20 FPS 回调不会重置或绕过 2 FPS 稳态时钟。
- 稳态 2 FPS 不提前重复帧。
- 突发结束恢复稳态时钟。
- 非单调时间戳和非正配置拒绝。
- 已入队关闭事件始终优先于端点结算；普通批次和静默时钟到期边界中的尺寸变化都会在返回任何端点前拒绝。
- 探针默认使用 20 FPS 捕获、2 FPS 稳态和 100ms 静默窗。
- 既有动画稳定、合法着验证、多步歧义暂停和窗口关闭路径继续回归。

## 6. 遗留风险和下一步门

1. 真实单步中间帧仍缺失，不能据此调整 0.02 语义间距门。
2. 100ms 静默窗是采样策略默认值，不是识别阈值；某些主题动画可能产生超过 100ms 的中间停顿，届时系统会保守地暂停，而不会静默接受。
3. 当前探针只观察一着并退出。正式同步循环需要在接受后继续处理已经排队的人机回应，但不得丢弃下一帧。
4. 下一次现场验证应在监听显示 `BASELINE_READY` 后立即手工走一着；若正确端点被捕获但严格观察器仍暂停，应收集多组真实裁片后改进特征，不能降低门槛。
5. 只有真实突发端点和严格观察器共同通过后，才进入 Pikafish 最小集成。
