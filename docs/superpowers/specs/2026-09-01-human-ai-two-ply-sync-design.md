# 人机练习模式双步原子同步设计

**日期：** 2026-09-01

**状态：** 已获用户批准，进入测试驱动实施

**适用范围：** 可见、无遮挡的天天象棋人机练习局

**依赖规范：** `docs/superpowers/specs/2026-08-30-visual-evidence-loop-design.md`

## 1. 背景与目标

真实冒烟证明，天天象棋中“用户落子 → 人机立即应手”可能发生在同一段连续动画里。捕获链路能看到完整变化，但在两步之间不一定出现足够长的稳定画面。严格单步同步会按设计拒绝这种变化并保留旧局面，安全性正确，但无法连续跟局。

本设计只为显式选择的“人机练习”模式增加一个受限例外：当严格单步观察无法解释一个完整稳定变化段时，允许从当前已确认局面枚举“用户一步 + 人机一步”的合法走法链。只有唯一、高置信、可由最终画面解释的两步链才一次性提交；其余情况全部暂停等待恢复。

目标是恢复人机练习中的连续同步能力，同时保持以下不变量：

- 不点击、不自动走棋、不注入、不读取微信进程内存。
- 不在真人在线对局中使用实时建议。
- 任何时候都不静默接受不确定局面。
- Pikafish 和 DeepSeek 只能收到已经确认的最终局面。

## 2. 模式边界

新增显式模式：

```python
class SyncMode(str, Enum):
    STRICT_SINGLE = "strict_single"
    HUMAN_VS_AI = "human_vs_ai"
```

- 默认值必须是 `STRICT_SINGLE`。
- `HUMAN_VS_AI` 只能由用户在创建或重新连接同步会话时明确选择，不能根据窗口标题、响应速度或画面内容自动推断。
- 切换模式必须结束旧会话、清空临时帧和候选，并从用户确认的 `BoardState` 重新开始。
- 残局训练、手工 FEN 检查和赛后复盘继续使用严格单步模式。
- 严格单步模式的既有拒绝门、测试门和阶段 C 指标保持不变。

人机模式仍优先执行严格单步观察。如果两步之间出现了可确认的稳定平台，系统应先提交第一步，再在下一段变化中提交第二步。只有两步被同一连续动画段合并时，才启用双步候选观察。

## 3. 核心数据契约

### 3.1 单步契约保持不变

`LegalMoveDiffObserver`、`MoveProposal` 和现有单步证据继续代表“一帧已确认局面到下一帧稳定局面的一步变化”。不得为了双步支持而降低其阈值或放宽意外变化检查。

### 3.2 新增双步提议

双步观察使用独立类型，避免把两个 UCI 走法塞进单步字段：

```python
@dataclass(frozen=True)
class MoveSequenceEvidence:
    candidates: tuple[SequenceCandidateEvidence, ...]
    changed_points: tuple[BoardPoint, ...]
    global_diff: float
    rejection_reasons: tuple[str, ...]
    feature_version: str

@dataclass(frozen=True)
class MoveSequenceProposal:
    status: ObservationStatus
    moves: tuple[Move, ...]
    evidence_score: float
    evidence: MoveSequenceEvidence
```

硬约束：

- `status == ACCEPTED` 时 `moves` 必须恰好包含 2 步。
- 非接受状态时 `moves` 必须为空。
- 不允许返回 3 步或更多步，也不允许只返回候选链的第一步。
- 候选证据必须包含绝对分数、与第二名的差距、预期变化点、意外变化点和拒绝原因。

`TrackingUpdate` 和 `LiveSyncUpdate` 将 `moves: tuple[Move, ...]` 作为规范字段。单步接受时长度为 1，双步原子接受时长度为 2，其他状态为空。若迁移期间保留旧 `move` 属性，它只能在长度为 1 时返回该步；长度为 0 或 2 时必须返回 `None`，避免调用方误把双步事件当成一步。

现有 `StateCommitter` 扩展为同一条规则转换边界：

```python
class StateCommitter(Protocol):
    def commit(self, board: BoardState, move: Move) -> BoardState: ...
    def project(self, board: BoardState, moves: tuple[Move, ...]) -> BoardState: ...
    def commit_sequence(self, board: BoardState, moves: tuple[Move, Move]) -> BoardState: ...
```

`project()` 只返回不可变的假设局面，不发布状态；`commit_sequence()` 重新验证完整链并返回最终局面。两者都必须通过同一个规则实现，不能出现“评分时合法、提交时使用另一套棋规”的分叉。

已接受更新还必须携带：

- `before_position_id`：提交前的确认局面。
- `after_position_id`：全部走法提交后的确认局面。
- `moves`：按真实先后顺序排列。
- `sync_mode`：产生该更新的显式模式。

## 4. 观察算法

### 4.1 触发条件

只有以下条件全部满足，跟踪器才可从单步观察转入双步观察：

1. 会话模式为 `HUMAN_VS_AI`。
2. 已检测到真实运动，并等到动画结束和最终画面稳定。
3. 从上一个确认帧到最终稳定帧的窗口、尺寸、棋盘几何和方向均未变化。
4. 严格单步观察未接受，并明确报告“多个合法变化点”或“候选不唯一”等可由合并走法解释的原因。
5. 单步观察没有报告上下文失效、画面遮挡、尺寸变化、几何越界、无变化或证据不足。

任一条件不满足都沿用现有暂停或恢复路径，不尝试双步猜测。

### 4.2 候选枚举

从提交前的确认 `BoardState` 开始：

1. 枚举当前行棋方的全部合法第一步 `m1`。
2. 通过 `StateCommitter.project()` 得到应用 `m1` 后的临时局面。
3. 枚举对方在临时局面中的全部合法应手 `m2`。
4. 再通过 `StateCommitter.project()` 得到候选最终局面。
5. 比较确认局面和候选最终局面，得到预期发生视觉变化的交点集合。

枚举和临时推演必须使用现有棋规层。`StateCommitter` 仍是唯一包装 `apply_move()` 的同步组件；视觉层不得自行实现棋规，也不得修改确认 `BoardState`。

### 4.3 视觉评分

第一版不识别整张 90 点棋盘，也不引入 ONNX。每个两步候选只评分与其预期变化相关的交点，并用其余局部差异约束意外变化。

固定主题的模板档案从一盘经用户确认的标准初始棋盘自动提取红黑 14 类棋子和空位模板。手工 FEN 会话可以复用同一主题档案；若候选所需模板缺失或主题已经变化，该候选不能接受，并提示重新建立模板档案。

评分至少包含：

- 预期变化点是否属于实测局部差异的显著点。
- 各变化点的最终裁片是否符合候选最终局面的棋子或空位模板。
- 起点变空、终点出现预期棋子以及吃子替换等语义是否一致。
- 候选预期不变的交点是否出现无法解释的强变化。
- 点选高亮、棋子阴影、动画残影和全局亮度变化是否触发既有抑制项。

两步可能涉及 2 至 4 个不同交点，包括两步共享交点、吃子和第二步吃掉第一步棋子的情况。评分实现必须按“提交前局面 → 候选最终局面”的实际差分生成交点集合，不能假设固定为四点。

只有同时满足以下门槛的候选可以接受：

- 候选链中的两步均合法。
- 最佳候选超过固定绝对阈值。
- 最佳候选相对第二名超过固定唯一性差距。
- 所有必要的起点、终点和最终模板证据完整。
- 没有超过阈值的意外变化点。
- 重新用同一输入评分可得到相同排序和结果。

0 个或多个合格候选均返回 `AMBIGUOUS` 并暂停。门限只能通过冻结开发集确定，不允许在真实运行时自适应降低。

## 5. 跟踪与原子提交

跟踪器在一次运动簇开始后必须保留最后确认帧作为基线，直到出现以下三种终态之一：

- 严格单步被接受。
- 唯一双步链被原子接受。
- 证据不充分，进入 `PAUSED_AMBIGUOUS`。

双步提交必须满足事务语义：

1. `StateCommitter` 在不可见的临时状态上依次验证并应用两步。
2. 两步全部成功后，才同时替换确认局面和确认帧。
3. 任一步失败、位置编号不匹配或会话代次已经过期时，丢弃整个结果。
4. 不得把第一步作为中间确认局面对外发布，也不得让引擎或教练看到部分结果。

`StateCommitter` 仍是唯一允许包装规则层 `apply_move` 的同步组件。候选枚举只能调用其纯 `project()` 接口，不能调用 `commit()`、`commit_sequence()` 或更新会话状态；只有跟踪器在核对当前 `position_id` 和会话代次后才能请求原子提交。

三步或更多步合并不在本版本支持范围内。即使视觉证据看似充分，也必须暂停并要求用户用当前 FEN 恢复。

## 6. UI 与下游事件

人机练习模式需要在独立窗口中明确显示当前同步模式，不隐藏安全差异。

- 单步接受：显示一条记谱，例如 `已同步：炮二平五`。
- 双步接受：按顺序显示两条记谱，例如 `已同步：炮二平五 · 马8进7`。
- 镜像棋盘只发布原子提交后的最终局面；最近一步高亮显示第二步，走法历史同时追加两步。
- 双步不唯一：显示 `检测到连续两步，但无法唯一确认；已暂停`，并提供重新观察或手工 FEN 恢复。
- 模式切换：要求重新确认局面，不沿用旧会话的待决证据。

Pikafish 只接收 `after_position_id` 对应的最终局面。旧代次的快速、加深分析或 DeepSeek 回答仍必须被丢弃。第一版不在原子提交过程中为不可见的中间局面触发实时分析；之后可以在复盘模块中离线评估用户第一步，但不能改变同步提交规则。

## 7. 错误与恢复

下列情况必须失败关闭：

- 目标窗口关闭、最小化、被遮挡或无法唯一选择。
- 捕获时间戳倒退、帧尺寸变化或棋盘四角超出边界。
- 稳定判定超时或动画持续不结束。
- 单步和双步候选都不唯一。
- 评分结果缺少模板、出现非有限数值或特征版本不匹配。
- 提交时 `position_id` 已变化，或分析结果属于旧代次。

暂停时必须保留最后一个已确认局面，不用观察到的最终画面覆盖它。恢复方式为：

1. 用户恢复窗口与棋盘尺寸后重新观察。
2. 用户确认当前局面仍等于最后确认局面后继续。
3. 若实际已经多走，用户输入当前 FEN，创建新会话并重新标定。

## 8. 隐私与诊断数据

- 默认不保存完整窗口截图。
- 不保存窗口标题、昵称、头像、账号信息或 DeepSeek API Key。
- 现有 `EndpointSampleV1` 只表示单步四元组，不得复用其 `actual_uci` 字段伪装双步事件。
- 双步诊断需要独立的 `TransitionSampleV2`：记录两个 UCI 走法、特征版本、匿名位置编号、预期变化交点以及这些交点的 48×48 小裁片。
- 调试样本默认关闭，开启后只写入 Git 忽略的 `.local/`，沿用可配置的 7 天 UTC 过期清理。
- 在 `TransitionSampleV2` 实现前，双步运行只能输出内存指标，不得回退到保存完整截图或错误写入 V1。

开发期间经用户临时授权的电脑控制只用于指定的测试落子，操作完成即结束控制。这不是产品能力，不得进入运行时代码或产品说明中的自动走棋功能。

## 9. 测试与验收门

### 9.1 自动测试

必须覆盖：

- 默认模式仍是严格单步，且严格模式继续拒绝两步合并。
- 人机模式能分别处理“有稳定平台的两个单步”和“没有稳定平台的原子双步”。
- 两步链顺序正确、双方轮换正确、每一步均由规则层验证。
- 共享交点、普通吃子、第二步吃掉第一步棋子以及 2、3、4 个最终变化交点。
- 0 个候选、多个候选、阈值不足、意外变化和三步合并均暂停。
- 第二步提交失败时不泄漏第一步，确认局面和确认帧均保持不变。
- resize、遮挡、窗口关闭、重复关闭、过期代次和错误 `position_id`。
- UI 同时显示两步记谱，镜像棋盘只收到最终局面。
- Pikafish 和 DeepSeek 只响应最终位置，旧结果不得显示。
- `TransitionSampleV2` 的隐私字段、默认关闭和过期清理。

所有功能继续按失败测试、最小实现、回归验证的顺序开发。

### 9.2 独立数据门

严格单步的阶段 C 数据集和指标完全沿用原规范，不与双步样本混算。

人机双步模式建立单独冻结门：

- 至少 30 个新会话中的真实两步合并事件。
- 至少 30 个应拒绝事件，覆盖多候选、点选高亮、连续动画、遮挡、resize 和三步合并。
- 被自动接受的两步链、顺序和最终 FEN 必须 100% 正确，错误接受数必须为 0。
- 有效两步事件自动接受覆盖率目标不低于 80%；未达到只影响可用性，不得放宽错误接受硬门。
- 最终画面稳定到同步决策的 P95 不超过 500 ms。

在该独立门通过之前，人机双步模式可以用于诊断和人工核对，但不得自动触发实时 Pikafish 或 DeepSeek。通过后只为该模式打开最终确认局面的分析，不影响其他模式的门状态。

## 10. 实施切片

后续实施计划应拆成可单独回退的四个切片：

1. 模式、双步证据类型和规则枚举，只使用合成棋盘与假帧。
2. 双步视觉评分、跟踪器原子提交和失败关闭测试。
3. UI 事件迁移、最终局面分析触发和 `TransitionSampleV2`。
4. 一次真实人机冒烟、冻结数据采集工具和阶段 C 报告。

每个切片只在相关聚焦测试通过后进入下一个切片。真实冒烟只在前三个切片完成并通过全量自动门后执行。

## 11. 非目标

本设计不包含：

- 自动点击或代替用户走棋。
- 真人在线对局实时建议。
- 三步或更多步的视觉追赶。
- 通用主题识别、ONNX 全盘检测或自动棋盘定位。
- 遮挡、最小化窗口或后台不可见捕获保证。
- 在不确定证据下自动选择最像的一条变化线。

## 12. 兼容与回退

- 未显式选择人机模式的现有调用方行为不变。
- 双步实现必须作为严格单步之后的受限分支，不修改现有单步门限。
- 若双步功能发生异常，可关闭 `HUMAN_VS_AI` 入口并完整回退到严格单步同步。
- 数据、UI 和下游消费者必须以 `moves` 元组为准，不能通过取最后一步掩盖原子事件。

本规范已获用户批准；具体实施按 `docs/superpowers/plans/2026-09-01-human-ai-two-ply-sync.md` 执行。
