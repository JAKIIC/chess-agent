# 天天象棋学习助手设计说明

**日期：** 2026-08-28  
**状态：** 已根据需求讨论定稿，供实施计划使用  
**目标平台：** Windows 10 1903+ / Windows 11，64 位  
**目标程序：** `C:\Users\lenovo\Desktop\天天象棋.lnk` 启动的微信小程序

## 1. 产品目标

构建一个仅用于人机练习、残局训练和赛后复盘的独立 Windows 桌面助手。助手绑定微信中的天天象棋窗口，维护一份与其同步的镜像棋盘；棋局每完成一步，助手自动识别并验证该走法、更新镜像局面、调用本地 Pikafish 分析，并用 DeepSeek 把引擎证据解释成可追问的中文教学建议。

产品的核心原则是“引擎负责正确，大模型负责讲懂”。任何具体走法、评分和变化线都必须来自本地规则层或 Pikafish；DeepSeek 不读取截图，不独立决定走法，也不能把未经验证的新走法展示成结论。

## 2. 明确不做的内容

- 不模拟鼠标点击，不替用户落子，不控制微信或天天象棋。
- 不用于真人在线对局中的实时提示；首次连接前必须确认当前是学习场景。
- 不安装中间人证书，不代理或解析微信网络流量。
- 不注入微信进程，不读取其内存，不逆向小程序内部协议。
- 不把屏幕截图上传给 DeepSeek；云端只接收结构化文本证据。
- 第一版不建设账号、云同步、排行榜、社交或联网题库。

## 3. 用户流程

1. 用户启动学习助手。
2. 助手可调用现有快捷方式打开天天象棋，快捷方式仅承担启动作用。
3. 用户在窗口列表中选择天天象棋所在的微信窗口，并确认学习模式。
4. 助手自动定位棋盘；首次或定位失败时，用户点击棋盘四角完成一次标定。
5. 助手完整识别当前 9×10 棋盘和红黑方向，在镜像棋盘中显示结果；初始行棋方由用户在确认框中选择，因为仅凭静态棋子布局不能可靠推断轮到谁走。
6. 用户确认初始同步结果和行棋方；之后助手在每个合法半回合后自动切换行棋方，只接受“连续稳定且构成合法一步”的局面变化。
7. 每次同步成功后，镜像棋盘高亮刚走棋子的起点和终点，并立即给出快速分析。
8. Pikafish 继续加深分析，界面逐步更新形势、候选着和主要变化。
9. 用户可以按分级提示逐层查看答案，也可以询问“为什么”“我的想法如何”“对方威胁是什么”。
10. 对局结束后，助手保存本局棋谱、评分曲线、关键失误和教练问答，生成复盘入口。

## 4. 总体架构

```text
微信天天象棋窗口
    ↓ Windows Graphics Capture（只读）
棋盘定位与 90 点图像裁切
    ↓ ONNX 棋子分类 + 多帧稳定
ObservedPosition
    ↓ 前后局面对比 + 象棋合法性验证
MoveEvent / BoardState
    ├─→ PySide6 镜像棋盘
    ├─→ SQLite 棋局记录
    └─→ Pikafish UCI 进程
             ↓ MultiPV、评分、主要变化
         EngineAnalysis
             ↓ 事实提取与证据封装
         CoachEvidence
             ↓ DeepSeek V4（文本 JSON）
         CoachExplanation
             ↓ 独立窗口教学面板
```

各层通过不可变数据对象传递信息。画面捕获不知道象棋规则；识别层不知道引擎；Pikafish 层不知道 UI；DeepSeek 层只读取已验证证据。这样可以单独替换捕获库、识别模型、引擎版本或大模型，而不改动其他层。

## 5. 技术基线

- Python `>=3.12,<3.13`；开发机使用已安装的 Python 3.12.4。
- PySide6 `>=6.8,<6.10`：独立桌面窗口、线程信号、镜像棋盘和设置界面。

  兼容性说明：在锁定的 Python 3.12.4 Anaconda Windows 环境中，PySide6 6.10.3/6.11.2 的 QtCore 会通过新增的通用 ICU 依赖加载 `icuuc.dll`，并因 WinError 127 失败；PySide6 6.9.3 已验证可正常加载。项目保留 Qt 运行时导入测试，只有更新版本 wheel 通过该测试后才重新评估此上限。
- `windows-capture==2.0.1`：通过 Windows Graphics Capture 捕获指定窗口。
- OpenCV `>=4.10,<5`、NumPy `>=2,<3`：棋盘裁切、图像归一化和变化检测。
- ONNX Runtime `>=1.20,<2`：本地棋子分类推理，默认 CPU Execution Provider。
- Pikafish `2026-01-02`：独立 UCI 子进程；不把引擎代码链接进 Python 进程。
- HTTPX `>=0.28,<1`：直接调用 DeepSeek Chat Completions API。
- Pydantic `>=2.9,<3`：跨模块数据契约和 DeepSeek JSON 校验。
- `keyring>=25,<26`：把 DeepSeek API Key 保存到 Windows Credential Manager。
- SQLite：使用 Python 标准库 `sqlite3`，不增加 ORM。
- pytest、pytest-qt、pytest-cov、ruff、mypy：测试、界面测试、覆盖率和静态检查。
- PyInstaller `>=6,<7`：生成 Windows 目录版应用。

## 6. 核心数据契约

### 6.1 BoardState

- `pieces`: 长度 90 的不可变元组，顺序固定为从黑方视角顶部到红方视角底部逐行存储。
- `side_to_move`: `"w"` 或 `"b"`。
- `orientation`: `RED_BOTTOM` 或 `BLACK_BOTTOM`，只影响显示和截图坐标映射，不改变内部棋盘顺序。
- `ply`: 从本次会话确认局面起计算的半回合数。
- `fen`: 由 `pieces` 和 `side_to_move` 确定性生成。
- `position_id`: 标准化 FEN 的 SHA-256 前 16 字节十六进制值，用于丢弃过期异步结果。

### 6.2 ObservedPosition

- 完整 90 点分类结果、每点置信度、棋盘区域、方向判断、捕获时间和图像尺寸。
- 仅当连续 3 次观察结果相同、总跨度不超过 600 ms 且最低关键棋子置信度不低于 0.85 时，才成为稳定观察。

### 6.3 MoveEvent

- `before_position_id`、`after_position_id`、UCI 坐标走法、中文记谱、移动方、是否吃子、是否将军、观察置信度和时间戳。
- 必须由前后局面对比得到，并通过规则层验证；识别层不能直接创建已确认走法。

### 6.4 EngineAnalysis

- `position_id`、搜索时长、最终深度、节点数、MultiPV 候选列表。
- 每个候选包括 UCI 走法、中文记谱、当前行棋方视角评分、将杀距离、WDL（若引擎提供）和主要变化。
- UI 只接受与当前 `position_id` 相同的结果。

### 6.5 CoachEvidence

- 当前 FEN、用户执方、阶段、最近 12 个半回合、子力统计、王安全事实、直接吃子/将军事实、前三候选、候选变化线、用户实际走法损失和允许引用的中文走法表。
- 走法以稳定 ID（`candidate_1`、`candidate_2`、`candidate_3`）提供给 DeepSeek。模型返回候选 ID，程序再渲染为中文走法，防止模型改写坐标。

## 7. 实时同步状态机

状态固定为：

```text
DISCONNECTED
  → SELECTING_WINDOW
  → CALIBRATING
  → CONFIRMING_INITIAL_POSITION
  → WATCHING
  → ANIMATION_DETECTED
  → WAITING_FOR_STABLE_FRAMES
  → VALIDATING_MOVE
  → SYNCED
  → ANALYZING
  → WATCHING
```

异常进入 `SYNC_WARNING`，此时保持最后一个已确认的 `BoardState`，不向引擎或 DeepSeek发送可疑局面。系统自动尝试 3 次完整重识别；仍失败则显示“重新标定”和“手工纠正”入口。窗口关闭、最小化产生空帧或捕获会话失效时进入 `PAUSED`，窗口恢复后重新完整识别并要求局面一致才继续。

稳定画面下目标采样率为 5 FPS。仅棋盘区域感知哈希变化超过阈值时运行完整 90 点分类；动画期间最多提升到 10 FPS。这样避免对每一帧重复推理。

## 8. 棋盘定位与识别策略

### 8.1 定位

- 保存棋盘四角相对于窗口客户区的归一化坐标，适配窗口移动和等比例缩放。
- 自动定位通过棋子检测框与 9×10 网格几何一致性完成；自动结果必须在 UI 中可见。
- 自动定位置信度不足时使用四角点击标定；标定结果按窗口应用名、分辨率和 DPI 档位保存。

### 8.2 模型选择门

第一轮同时评估两个有明确 MIT 来源的候选识别资产：`yingwang/xiangqi-bot` 的天天象棋 15 类 ONNX 模型，以及 `dffge552/xiangqi-pwa-offline` 的检测与分类模型。评估集固定包含不少于 200 张本机稳定帧，覆盖红黑在下、100%/125%/150% DPI、开中残局和选中棋子高亮。

采用条件为：稳定帧整盘完全正确率不低于 99%，15 类宏平均 F1 不低于 99.5%，单帧 CPU 推理不高于 100 ms。若两者均不满足，则使用本机截图裁出至少 2,000 个棋盘交点补丁，训练 15 类轻量分类器并导出 ONNX；训练脚本只作为开发依赖，不进入发布包。

### 8.3 时序校验

- 首次同步进行完整 90 点识别并由用户确认。
- 初始确认界面必须显式选择红方或黑方行棋；确认后每个合法 MoveEvent 自动翻转行棋方。
- 后续先比较交点图像变化，只重点重识别变化点及低置信点，再周期性进行完整复核。
- 前后局面必须能解释成唯一合法走法；吃子允许一个起点消失、一个终点类别变化。
- 对“棋子选中放大”“落子阴影”“将军动画”等瞬态效果使用多帧投票，不更新已确认局面。

## 9. 象棋规则与记谱

内部坐标使用 Pikafish UCI 风格 `a0` 到 `i9`，内部棋盘方向永远标准化为红方在下。规则层负责：

- 七类棋子的几何走法、马腿、象眼、炮架、九宫、过河限制。
- 将帅照面、自陷将军和走后己方被将军的非法性判断。
- 合法走法生成、应用走法、FEN 解析/生成。
- 红黑双方中文记谱、同一路同类棋子的前后中标记。
- 用规则层验证画面差分得到的走法；长将、长捉等完整竞赛判罚不作为第一版同步阻断条件，但原始局面与重复次数必须记录供复盘使用。

## 10. Pikafish 分析

Pikafish 由单独受管进程运行，通过标准输入输出通信。启动后执行 `uci`、`isready`，设置 `Threads=2`、`Hash=256`、`MultiPV=3`。每个新局面采用两阶段分析：

1. 快速阶段：`go movetime 500`，目标是在局面同步后约 1 秒内显示初步评分和候选着。
2. 加深阶段：`go movetime 3000`，替换快速结果并生成教练证据。

新局面到达时发送 `stop`，并通过 `position_id` 丢弃旧结果。引擎崩溃最多自动重启一次；第二次失败后禁用分析但继续棋盘同步，并向用户显示明确诊断。

评分始终归一化为红方视角存储，UI 根据用户视角显示。将杀分数与普通子力分数分开表示，不能把 mate 值换算成虚假的胜率。

## 11. DeepSeek 教练

默认使用 `deepseek-v4-flash` 的非思考模式生成低延迟解释；用户主动选择“深度复盘”时使用 `deepseek-v4-pro` 并启用高推理强度。调用 `/chat/completions`，要求 `response_format={"type":"json_object"}`。

返回 JSON 固定包含：

- `position_summary`: 一句话形势概括。
- `main_plan`: 当前最重要的计划。
- `candidate_id`: 必须是证据包允许的候选 ID。
- `why`: 该候选解决的问题。
- `opponent_threat`: 对方最主要威胁。
- `alternatives`: 其他候选的差别，只能引用允许 ID。
- `training_question`: 给用户的一道思考题。
- `confidence`: `high`、`medium` 或 `low`。

Pydantic 校验失败、候选 ID 越界或文本中出现未在允许表中的具体走法时，结果不能直接展示；系统重试一次，仍失败则退回本地模板解释。API 超时为 12 秒。API Key 存在 Windows Credential Manager 中，日志只记录请求 ID、耗时、模型和 token 用量，不记录密钥或完整对话。

## 12. 独立窗口设计

第一版主窗口采用左右结构：

- 左侧约 58%：镜像棋盘、上一步高亮、候选箭头和局势曲线。
- 右侧约 42%：连接状态、当前形势、分级提示、前三候选、主要变化、AI 教练对话。
- 底部状态栏：当前行棋方、识别置信度、引擎阶段、DeepSeek 状态和最近一次同步时间。

提示默认采用学习式逐层揭示：先显示局面主题，再显示应关注的棋子，再显示候选走法，最后显示主要变化。用户可以在设置中选择直接展示前三候选。窗口不覆盖天天象棋，不注册自动点击热键。

## 13. 数据与隐私

SQLite 数据库保存在用户本地应用数据目录，包含：

- `sessions`: 模式、执方、开始结束时间、结果。
- `positions`: 标准化 FEN、局面编号、同步置信度。
- `moves`: UCI、中文记谱、时间、是否吃子/将军。
- `analyses`: 引擎版本、参数、评分和 PV JSON。
- `coach_messages`: 用户问题、结构化证据摘要和教练回答。
- `sync_incidents`: 失败类型、恢复方式和诊断截图路径。

诊断截图默认关闭。用户开启后只在同步失败时保存裁切后的棋盘区域，不保存整个桌面，并在 7 天后删除。数据库和截图均不自动上传。

## 14. 错误处理

- 找不到快捷方式：允许手工启动微信并从窗口列表选择。
- 找不到目标窗口：保持选择界面并每 2 秒刷新，不崩溃。
- 棋盘定位失败：转四角标定，不猜测坐标。
- 识别不稳定：保持上一局面，显示黄色同步警告。
- 非法或多步变化：执行完整重识别，仍无法唯一解释时要求手工确认。
- 窗口最小化或关闭：暂停捕获和引擎，不伪造新局面。
- Pikafish 缺失或不兼容：同步功能仍可用，分析面板显示安装向导。
- DeepSeek 未配置、超时或余额不足：引擎分析继续可用，使用本地模板解释。
- 数据库写入失败：切换只读会话并向用户提示导出当前棋谱。

## 15. 测试策略

- 单元测试：FEN、坐标、规则、中文记谱、局面差分、状态机、UCI 解析、证据校验。
- 图像回放测试：固定截图和录制帧离线重放，不依赖正在运行的微信。
- 合成测试：生成不同缩放、亮度、选中高亮和动画模糊的棋子补丁。
- 集成测试：使用假捕获源、假 ONNX 分类器、假 UCI 引擎和本地 HTTP 假 DeepSeek 服务。
- UI 测试：连接流程、同步警告、候选展开、过期分析不显示、API 错误降级。
- 本机验收：微信小程序真实窗口、100%/125%/150% DPI、红黑双方、窗口移动和缩放。

第一版发布门槛：

- 10 盘完整人机对局的走法序列与人工记录完全一致；每盘至少 40 个半回合。
- 稳定画面整盘识别准确率不低于 99%，错误局面不得进入分析层。
- 落子动画结束到镜像棋盘更新的 P95 不高于 1.0 秒。
- 快速候选展示 P95 不高于 2.0 秒；DeepSeek 失败不阻塞同步和引擎结果。
- 在 30 分钟连续运行中无崩溃、无 Pikafish 残留进程、无数据库损坏。
- API Key、完整截图和用户隐私信息不出现在日志中。

## 17. 实施边界

项目分为五个可独立执行和验收的里程碑组：M1 Foundation（Tasks 1-8：工程、领域内核、安全配置、桌面壳、窗口捕获与标定）、M2 Recognition and Sync（Tasks 9-12：识别资产门、ONNX 识别、多帧稳定与可靠同步）、M3 Pikafish Analysis（Tasks 13-14：可审计受管引擎与两阶段本地分析）、M4 DeepSeek Coach（Tasks 15-17：结构化证据、严格校验的教练与学习交互）、M5 Persistence and Release（Tasks 18-21：本地复盘、恢复与隐私、Windows 打包和真实验收）。每个任务必须先有失败测试，再实现最小功能，通过后提交；每个里程碑只有在测试、独立评审、隐私扫描和干净工作树四项门槛全部满足后才允许推送。不能在识别可靠性未达标前进入依赖该结果的后续里程碑，也不能加入自动化操作，因为自动化操作本身不属于本项目。
